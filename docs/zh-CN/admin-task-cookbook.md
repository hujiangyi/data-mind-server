# DataMind 管理员任务配方

这份手册按照“我想完成什么”组织内容。每个配方都可以直接复制示例语句，再根据实际对象替换账号、数据源、数据库和表名。

## 使用方法

每次任务都遵循同一条简单路径：

```text
说清目标
→ 回答系统的问题
→ 核对影响范围
→ 确认执行
→ 等待必要分析
→ 用实际账号验证
```

系统不会把没有确认的猜测当作事实，也不会把不支持的范围改写成任意查询条件。

## 配方一：创建平台用户

### 适用场景

新员工或服务账号需要登录 DataMind。

### 推荐说法

```text
创建平台用户 zhangsan，真实姓名是张三，角色是普通用户。
```

### 你需要核对

- 账号拼写；
- 真实姓名；
- 角色是否符合岗位；
- 是否创建了不必要的管理权限。

### 完成后

通过受信任的方式交给员工初始登录信息，并提醒首次登录修改密码。不要把密码写入 AI 对话、任务备注或截图。

## 配方二：确认用户当前权限

### 适用场景

需要回答“这个人现在能看什么”或“为什么查不到数据”时，
请先在用户管理和权限管理页面查看真实的当前状态。

### 结果重点

分别看：

- 账号是否正常；
- 是否加入预期权限组；
- 权限组是否访问目标表；
- OWNER 数据范围是否已经可用；
- 数据源身份是否唯一；
- 是没有权限，还是权限已存在但数据范围仍在等待。

查看结果只以管理页面显示的当前状态为准，不要把聊天中的描述当作权限事实。

## 配方三：让用户只能查询自己负责的数据

### 适用场景

员工需要查询与自己负责关系对应的客户、订单或其他业务记录。

### 推荐说法

```text
让账号 zhangsan 查询 crm 数据源、crm 数据库的 orders 表中
负责人字段等于其本人数据源身份的记录。
```

### 系统会确认

- zhangsan 是否唯一；
- crm 数据源是否唯一；
- crm 数据库和 orders 表是否存在；
- 表中是否有可靠的负责人字段；
- zhangsan 在数据源中是否有唯一身份；
- 是否已有相同授权；
- 这次配置是否只落在“本人负责记录”的范围内。

### 完成标准

```text
用户有目标表访问资格
负责人字段已经识别并可比较
数据源身份唯一且有效
本人身份匹配已经启用
普通用户实际查询只返回本人负责记录
```

### 不能替代的做法

不要把下面的表达当作同一件事：

```text
让 zhangsan 看销售组数据。
```

销售组是用户集合，不是一个共享的数据范围。应继续说明每个用户要查询与自己身份匹配的负责人记录。

## 配方四：停用账号

### 适用场景

员工离职、临时账号不再使用或账号需要被暂停。

### 推荐说法

```text
停用账号 temporary_user。
```

### 你需要核对

- 目标账号不是当前登录的管理员账号；
- 账号确实是需要停用的人；
- 是否有正在处理的权限申请或任务；
- 停用后是否需要进入精确页面检查关联权限。

这是会影响登录和访问的操作，确认前要仔细核对账号。

## 配方五：补充系统追问

### 同名用户

```text
AI 管家：发现两个张三，请补充账号或员工号。
管理员：选择账号 zhangsan，员工号 S-1024。
```

不要只回复“第一个”或“销售部那个”，除非系统已经明确列出了唯一候选。

### 多个候选表

```text
AI 管家：发现多个 orders 表，请补充数据源和数据库。
管理员：数据源是 crm，数据库是 crm。
```

### 缺少目标动作

```text
AI 管家：你希望新增权限、停用账号，还是只查看当前状态？
管理员：新增权限，但只能查询负责人字段等于本人身份的记录。
```

## 配方六：处理不支持的范围要求

### 错误说法

```text
让张三查看华东区数据。
```

```text
让销售部门只能查看本部门客户。
```

```text
让项目 A 的成员查看项目 A 的订单。
```

### 当前可执行的替代说法

```text
让账号 zhangsan 只能查询负责人字段等于其本人数据源身份的记录。
```

如果业务目标确实是区域、部门或项目隔离，目前需要进入人工评估流程，不能让 AI 管家自行创造新的数据范围。

## 配方七：OWNER 分析正在等待

### 你会看到什么

权限关系可能已经准备完成，但负责人字段分析或数据源身份匹配还没有达到可用条件。

### 正确处理

1. 等待系统完成分析；
2. 查看是否需要人工复核；
3. 如果字段识别不确定，进入数据范围管理；
4. 如果身份重复或冲突，进入身份绑定；
5. 完成后用目标用户账号实际查询。

### 不要做什么

不要为了让页面尽快显示成功而：

- 把数据范围改成全表；
- 让数据库账号拥有更大权限；
- 覆盖已有的冲突身份；
- 通过任意 SQL 条件绕过系统限制。

## 配方八：权限申请

### 适用场景

员工申请当前权限之外的数据访问。

### 推荐做法

管理员可以在审批中心查看申请背景、当前有效权限、目标数据源和数据表、
OWNER 数据范围状态以及身份绑定状态，并检查申请中是否包含系统不支持的
区域、部门、项目或全表范围。

最终批准仍由管理员在审批中心完成。批准前要确认申请对象、表、范围和验证方式；
批准后用目标账号进行实际查询。

## 配方九：任务无法自动完成

### 常见原因

- 用户或表无法唯一识别；
- 数据源元数据还没有同步；
- 负责人字段不明确；
- 分析结果需要人工复核；
- 数据源身份存在冲突；
- 执行后真实状态与计划不一致。

### 处理方式

先看页面给出的具体阻断原因，再选择：

```text
补充信息
查看数据源
进入数据范围管理
处理身份绑定
查看审批中心
回滚本次计划
转入人工处理
```

任务没有通过真实状态验证时，不应把它当作成功。

## 配方十：管理员的最短表达

在熟悉系统后，可以把大多数常规任务压缩成下面的句式：

```text
对 [用户] 做 [新增 / 停用 / 查看]，
针对 [数据源] 的 [数据库].[表]，
数据范围是 [本人身份匹配的负责人记录]。
```

例如：

```text
对 zhangsan 新增 crm 的 crm.orders 查询权限，
数据范围是本人身份匹配的负责人记录。
```

这比记忆菜单路径更快，也更不容易把用户、表和数据范围混淆。

## 最后检查

每次写入完成后都确认：

```text
□ 目标对象正确
□ 影响范围没有扩大
□ 数据范围仍然是本人身份匹配
□ 分析和身份状态清楚
□ 实际查询结果符合预期
```
