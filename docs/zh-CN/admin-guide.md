# DataMind 管理员操作指南

本文面向第一次接手 DataMind 的平台管理员，说明如何把分散在多个业务系统中的数据接入平台，并按照员工、岗位和业务范围分配可控的数据访问权限。

DataMind 的核心原则是：数据库连接凭据保留在服务端，AI 和普通用户只使用经过服务端校验的能力。管理员可以把数据源、用户、权限组、数据表和数据 API 集中管理，但不需要把生产数据库超级账号直接交给 AI。

## 1. 管理员登录

打开 DataMind Server 的网站地址，进入“登录”页面。

- 使用部署时已经存在的管理员账号登录；
- 如果是全新私有化安装，先按照项目交付信息确认初始管理员账号；
- 不要把管理员密码写入脚本、Issue、Release 说明或聊天记录；
- 首次登录后，建议在“系统设置”中确认管理员邮箱和密码策略。

Cloud 账号与 DataMind Server 的本地员工账号是两套身份：

- Cloud 账号用于服务访问 Cloud AI 和管理 Cloud API Key；
- Server 员工账号用于登录管理页面、分配数据权限和记录业务操作；
- 不要用 Cloud API Key 代替员工登录密码，也不要把员工密码配置给 AI 工具。

## 2. 添加数据源

添加数据源前，先确认 DataMind Server 所在服务器可以访问目标数据库。浏览器能够访问数据库管理工具，不代表服务器本身可以访问数据库。

操作路径：**数据源管理 → 添加数据源**。

1. 选择“关系库”或“Hadoop”；
2. 选择数据库类型，例如 MySQL、PostgreSQL、Oracle 或 SQL Server；
3. 填写数据源名称，名称应能体现业务系统和用途，例如 `sales-prod`、`finance-readonly`；
4. 填写服务器地址、端口、数据库名称、用户名和密码；
5. 点击“测试连接”；
6. 连接成功后选择需要纳入平台管理的数据库；
7. 保存数据源；
8. 在数据源列表中执行同步，生成数据库、数据表和字段元数据。

建议使用目标数据库提供的只读账号。DataMind 需要完成元数据读取、查询和受控的数据 API 操作时，应由管理员按实际业务需要配置数据库账号权限，不要默认使用数据库管理员账号。

数据源配置中的密码属于服务端敏感信息：

- 只在受信任的管理页面输入；
- 不要放入前端代码、公开仓库、Docker 镜像或截图；
- 修改数据库密码后，要同步更新数据源配置并重新测试连接；
- 数据库开启白名单或 TLS 时，要同时配置服务器出口地址和证书要求。

## 3. 同步和检查元数据

数据源保存后，进入数据源列表确认：

- 连接状态正常；
- 数据库数量符合预期；
- 数据表和字段已经同步；
- 最近同步时间已更新；
- 表数量没有异常减少。

可以在“数据目录”中按数据源、数据库和表名查看元数据，也可以在“SQL 查询”中选择数据源、数据库和数据表验证读取结果。

同步失败时，优先检查：

1. 数据库账号是否仍然有效；
2. Server 主机到数据库的网络和防火墙；
3. 数据库白名单、端口和 TLS；
4. 数据源类型是否选择正确；
5. 数据库是否有权限读取元数据；
6. 服务日志中的脱敏错误和同步时间。

不要为了绕过同步问题而扩大数据库账号权限。先修复连接、元数据权限或数据源配置。

## 4. 创建员工账号

操作路径：**用户管理 → 新增用户**。

填写：

- 用户名；
- 8 到 16 位登录密码；
- 真实姓名；
- 员工号；
- 可正常收信的邮箱；
- 角色和备注。

“管理员”“数据管理员”“API 操作员”“数据质量管理”“普通用户”和“业务用户”用于表达岗位职责。实际可访问哪些数据，仍然应通过权限组和数据授权明确配置，不建议仅依赖角色名称做安全判断。

员工离职、岗位变化或账号泄露时：

- 先编辑账号或删除账号；
- 移除其所在权限组；
- 检查其历史数据访问记录；
- 必要时撤销相关数据 API；
- 不要只修改前端显示名称而保留原有授权关系。

## 5. 创建权限主体和授权范围

操作路径：**权限管理 → 新增权限主体**。

一个权限主体可以理解为一个可复用的授权集合，例如：

- 销售华东组；
- 财务只读组；
- 仓库运营组；
- 项目经理组。

创建权限主体时填写名称和描述，描述应明确业务边界，不要只写“默认权限”或“全部权限”。

进入权限主体详情后，重点配置以下标签页：

### 用户授权

在“用户授权”中选择已经注册的员工账号。推荐按照岗位、部门和业务线建立权限组，再把用户加入权限组，避免逐个用户维护大量重复授权。

### 数据权限

在“数据权限”中选择数据源、数据库和数据表。遵循最小授权原则：

- 先授权必需的数据源；
- 再授权必需的数据库；
- 最后选择必需的数据表；
- 只授予完成工作所需的读权限或写权限；
- 不要因为 AI 需要理解字段，就把整个数据库全部授权。

对于包含负责人、部门、区域、租户或项目归属字段的表，应在授权前确认数据范围模型和身份映射。系统可以通过元数据和 AI 辅助识别候选负责人字段，但管理员必须检查分析结果，不能把低置信度结果直接当作正式授权。

### API 权限

如果团队发布了数据 API，在“API 权限”中只授予员工实际需要调用的接口。数据 API 的 SQL 模板、参数和结果范围仍应与对应的数据表权限保持一致。

## 6. 配置数据范围和身份映射

表级授权只能说明“用户可以接触哪张表”，不能自动说明“用户可以看这张表中的哪些行”。对于销售、客户、订单、项目等业务数据，还应配置数据范围和身份映射。

推荐流程：

1. 先同步目标表的字段和少量统计信息；
2. 确认表中存在负责人、员工号、用户 ID、姓名或登录名等关联字段；
3. 将目标表加入对应权限组；
4. 检查数据范围分析和待审核任务；
5. 对低置信度或多候选字段进入“审批中心”人工确认；
6. 为员工绑定其在业务系统中的外部身份值；
7. 使用该员工账号执行一条受保护查询；
8. 再使用没有授权的员工账号验证拒绝效果。

身份绑定必须保持唯一和可追溯。员工在不同业务系统中的账号可能不同，不要假设 Server 用户名一定等于业务数据库中的姓名或员工号。

## 7. 审批和日常授权变更

操作路径：**审批中心**。

管理员应定期处理：

- 待审批的表权限申请；
- 待审批的 API 权限申请；
- 被驳回申请的原因；
- 已撤回或已删除的历史申请。

批准前确认申请人的岗位、业务目的、目标数据表和权限类型。驳回时填写清晰原因，便于员工改正申请范围。

权限变更完成后，不要只检查页面提示，还要用目标员工账号实际验证：

- 授权的数据源是否可见；
- 未授权的数据源是否不可见；
- 授权表是否能正常查询；
- 超出数据范围的行是否被过滤；
- 未授权的 API 是否被拒绝。

## 8. 日常运营清单

### 每日

- 检查网站和 `/health`；
- 检查数据源连接状态和最近同步时间；
- 查看“审计日志”中的失败访问和异常用户；
- 查看“审批中心”的待处理申请；
- 检查数据质量和同步任务异常。

### 每周

- 复核管理员、数据管理员和 API 操作员名单；
- 复核权限组成员是否仍在对应岗位；
- 清理不再使用的数据源、表授权和数据 API；
- 抽查高敏感数据的访问记录；
- 检查备份、磁盘空间和日志保留策略。

### 发生人员或业务变化时

- 员工转岗：先移除旧权限，再加入新权限组；
- 员工离职：停用账号并复核其最近访问记录；
- 数据库迁移：先新建数据源测试，再切换业务授权；
- 表结构变化：重新同步元数据并检查数据范围分析；
- API 变更：重新测试参数、结果字段和权限边界。

## 9. 安全边界

DataMind 的安全边界由服务端执行，不能依赖浏览器按钮或 AI 自觉遵守。

- 普通员工只能看到服务端返回的授权数据；
- 管理员工具和普通员工工具应按身份分离；
- 修改客户端请求参数不能绕过服务端权限校验；
- 数据库账号、Cloud API Key 和员工密码必须分开保存；
- 生产环境建议使用 HTTPS 和 Nginx，并限制管理端来源；
- 公开反馈只提供脱敏日志、时间和错误类型，不提供完整凭据和客户数据。
