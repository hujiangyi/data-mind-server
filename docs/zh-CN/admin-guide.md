# DataMind AI 管理员任务手册

DataMind 的管理方式是 AI-first，但安全边界是服务端-first。

管理员用自然语言描述目标，管理员 Agent 负责查询控制库、识别对象、生成计划、提出问题、执行已确认的动作，并重新读取真实状态验证结果。数据源连接、权限申请审批和无法自动处理的冲突，仍然由管理员在精确管理页面完成。

Agent 不是开放式超级管理员。它只能从 DataMind 已注册的动作中选择，不能创造新的权限语义，也不能把自然语言直接变成任意 SQL 条件。

## 1. DataMind 当前权限模型

当前版本的数据范围能力只有一条主线：

```text
OWNER / DIRECT / EQUALS
```

含义是：

- `OWNER`：数据范围按负责人字段控制；
- `DIRECT`：负责人字段的值直接映射到数据源用户身份；
- `EQUALS`：查询时只匹配当前用户对应的外部身份值；
- 普通用户只能查询负责人字段等于其本人数据源身份的记录；
- 管理员仍然可以按照现有管理员规则查看全部数据。

当前支持的数据源类型为 MySQL 和 PostgreSQL。身份来自平台用户、数据源用户目录以及目标表负责人字段之间的映射。

当前不支持：

- 华东区、华南区等区域范围；
- 部门、岗位、项目或租户范围；
- 组织层级继承；
- 任意业务条件或表达式规则；
- `OR` 数据范围；
- 全表模式；
- 让一个用户集合共享一套全量行范围。

“销售组”可以作为权限组或用户集合存在，但它不代表“销售区域范围”。组内每一个普通用户仍然只能看到负责人字段与自己身份匹配的记录。

## 2. 管理员 Agent 能做什么

管理员可以直接描述以下目标：

```text
让张三可以查询客户订单表中与他本人相关的记录。
```

在对象唯一、身份可解析、分析通过后，Agent 会按以下顺序编排：

```text
识别张三
→ 确认目标数据源、数据库和表
→ 创建或更新权限组
→ 加入用户
→ 授权目标表
→ 触发 OWNER 字段分析
→ 匹配张三在数据源中的身份
→ 激活 OWNER / DIRECT / EQUALS 控制
→ 验证最终有效权限和查询策略
```

Agent 也可以协助：

- 创建、停用、恢复和重置平台用户；
- 创建和维护权限组及成员关系；
- 授权或撤销权限组的数据表访问；
- 触发和查询 OWNER 分析任务；
- 查看身份绑定、有效权限和待复核任务；
- 识别冲突并转入人工接管。

数据源连接参数不由 Agent 修改。数据库账号、密码和 API Key 不能写入对话、计划或普通任务日志。

## 3. “与我有关的数据”是什么意思

“与我有关的数据”不是模型自由判断，也不是一个可以任意扩展的业务标签。

它只表示：

1. 目标表存在真实的负责人、用户 ID、工号、账号名或姓名等人员关联字段；
2. 系统通过元数据和有限样本识别出可比较的负责人字段；
3. 该字段使用 `DIRECT` 映射；
4. 查询使用 `EQUALS` 比较；
5. 字段值等于当前用户在该数据源中的唯一外部身份值。

例如，目标表的 `owner_user_id` 值为 `u-1024`，张三在该数据源用户目录中的身份也是 `u-1024`，那么张三可以查询匹配该值的记录。其他用户不能因为加入同一个权限组就看到张三的记录。

原始业务样本不会进入 Agent 任务记忆。任务只保留对象 ID、状态、哈希和脱敏证据。

## 4. 如何与 Agent 交流

描述目标时，尽量包含：

- 平台用户账号、真实姓名或员工号；
- 权限组名称，或说明允许 Agent 创建权限组；
- 数据源名称；
- 数据库名称；
- 数据表名称；
- 是新增权限、撤销权限，还是只查看当前状态；
- 如果是数据范围，明确说“只能查询与本人身份匹配的负责人记录”。

推荐表达：

```text
让账号 zhangsan 查询 crm 数据源 crm 库 orders 表中与本人身份匹配的负责人记录。
```

Agent 会先查询控制库中的用户、权限组、数据源、数据库、数据表、授权状态、分析状态和身份绑定，不会仅凭自然语言猜测对象。

## 5. Agent 什么时候必须反问

出现以下情况时，Agent 必须停在 `NEEDS_CLARIFICATION`，不能继续写入：

- 找到多个同名用户；
- 找到多个同名数据表；
- “客户数据”“订单数据”等描述匹配到多个表；
- 用户没有说明新增还是撤销权限；
- 目标表没有可用负责人字段；
- AI 识别置信度低于 `0.80`；
- 数据源用户目录无法确定；
- 一个用户在同一数据源存在多个冲突身份；
- 目标权限组不唯一；
- 请求会影响大量用户、整库或大范围授权；
- 目标对象在计划生成后已经发生变化。

例如：

```text
管理员：给张三开通客户数据权限。
AI：发现两个“张三”，请补充账号、员工号或其他唯一信息。
管理员：销售部的张三，员工号 S-1024。
```

后续轮次会记住管理员已经选择的候选项，不会重新猜测。任务级记忆只服务于当前管理任务，不等同于普通聊天记录。

## 6. 哪些表达超出当前能力

以下表达不能直接配置：

```text
让张三看华东区数据。
让销售部门只能看本部门客户。
让项目 A 的成员看项目 A 的订单。
让张三看所有客户数据。
```

Agent 应明确说明原因，并给出当前可执行的替代表达：

```text
当前数据范围能力只支持“与用户本人身份匹配的数据”。
系统不能按华东区、部门或项目配置范围。
你是否要改为：让张三只能查询负责人字段等于其本人身份的记录？
```

Agent 不会生成以下策略：

```sql
WHERE region = '华东'
```

也不会通过前端角色、模型输出或 MCP 请求绕过服务端管理员校验。

## 7. OWNER 数据范围任务流程

当管理员确认“本人相关数据”目标后，系统按固定流程执行：

1. 唯一识别平台用户；
2. 唯一识别数据源、数据库和表；
3. 检查目标表是否已授权给权限组；
4. 新授权进入 `OWNER / PENDING_ANALYSIS`；
5. 触发现有异步分析任务；
6. 只从实际存在的字段中识别负责人候选；
7. 仅当 `DIRECT`、`EQUALS`、字段真实存在且置信度不低于 `0.80` 时，才允许自动激活；
8. 解析用户在该数据源中的唯一外部身份；
9. 身份唯一且无冲突时，创建或确认身份绑定；
10. 重新读取有效权限、分析状态和查询策略；
11. 分析未激活、身份未解析或验证失败时，普通用户查询保持阻断。

低置信度进入 `REVIEW_REQUIRED`，不允许 Agent 绕过复核直接放行。身份冲突也不会覆盖旧的有效绑定。

## 8. 计划、确认和执行

写操作会先生成结构化计划，页面或 MCP 会显示：

- 原始目标和 Agent 的理解；
- 受影响的用户、权限组和数据表；
- `OWNER / DIRECT / EQUALS` 固定策略；
- 当前分析和身份绑定状态；
- 预计新增、撤销或停用的对象；
- 风险等级；
- 执行后的验证方法；
- 可用的回滚动作。

高风险或会产生写入的动作必须处于 `WAITING_CONFIRMATION`，管理员确认后才能执行。

确定性检查始终优先于模型判断，至少包括：

- 当前请求是否在动作白名单内；
- 对象是否真实存在且唯一；
- 当前操作者是否是控制库中的真实管理员；
- 数据范围是否仍为 `OWNER / DIRECT / EQUALS`；
- 是否存在冲突身份；
- 是否会扩大到未声明的用户或数据表。

## 9. 任务记忆、恢复和失败处理

每个 Agent 任务有独立的任务账本：

- 任务生命周期和当前状态；
- 脱敏后的对话消息；
- 结构化计划；
- 每一个动作的输入、执行前后状态和验证结果；
- 可恢复检查点；
- 补偿动作和结果。

服务重启后，任务可以从最后一个检查点继续，不需要模型重新猜测原始目标。相同请求使用幂等键，不会重复创建成员关系或重复授权。

系统遵循以下处理规则：

- 同一个确定性错误不重复重试；
- 临时网络或 AI 超时只允许有限次重试；
- JSON 格式错误最多进行一次结构化修复；
- 执行后验证失败最多进行一次受限修正；
- 补偿失败或再次验证失败进入 `NEEDS_HUMAN`；
- 半失败任务不会标记为成功；
- 回滚失败会保留完整状态，等待管理员人工处理。

## 10. 精确管理页面和人工接管

Go 管理界面不是 Agent 的替代品，而是 Agent 处理不了的问题的精确工作台。

管理员仍然需要人工处理：

- 添加、修改和测试数据源连接；
- 审核低置信度 OWNER 字段分析；
- 解决冲突身份；
- 查看并批准权限申请；
- 处理 Agent 进入 `NEEDS_HUMAN` 的半失败任务；
- 检查异常授权、撤销权限和审计记录。

人工页面修改后，Agent 任务仍然会重新读取控制库状态，不把模型原来的描述当成事实。

## 11. 权限申请和最终审批

员工申请进一步权限时，申请会进入审批中心。Agent 可以帮助管理员整理申请上下文、查询当前有效权限和生成建议，但不能自动批准高风险申请。

管理员批准前应确认：

- 申请人和账号状态；
- 目标数据源、数据库和表；
- 现有权限组和 OWNER 状态；
- 身份绑定是否唯一；
- 申请是否意外要求区域、部门、项目或全表范围；
- 批准后如何验证，失败时如何撤销。

审批通过后，仍然要用目标员工账号实际查询验证。页面显示“成功”只说明控制库动作完成，不能替代最终的服务端策略验证。

## 12. MCP 管理入口

管理员 MCP 与 Web 管理工作台共享同一套任务和动作层。

- MCP Token 必须具有 `admin` scope；
- Go 服务还会校验控制库中的真实管理员角色；
- MCP 只能提交任务、补充信息、读取状态、确认或回滚；
- MCP 不能绕过 `WAITING_CONFIRMATION`；
- MCP 创建的任务可以在 Web 工作台继续处理；
- Web 创建的任务也可以通过 MCP 查询；
- `datamind_manage_identity` 继续用于身份绑定的精确处理；
- 数据查询仍然通过现有服务端 OWNER 策略执行。

## 13. 常用状态

| 状态 | 含义 |
| --- | --- |
| `NEEDS_CLARIFICATION` | 需要管理员补充唯一对象或阻断信息 |
| `PRECHECK_FAILED` | 前置条件不满足，未执行写操作 |
| `WAITING_CONFIRMATION` | 计划已经生成，等待管理员确认 |
| `EXECUTING` | 正在执行动作 |
| `WAITING_ANALYSIS` | 权限已写入，OWNER 分析仍在异步处理 |
| `VERIFYING` | 正在从控制库重新读取真实状态 |
| `SUCCEEDED` | 状态完成且验证通过 |
| `COMPENSATING` | 执行失败，正在执行已记录的补偿动作 |
| `ROLLED_BACK` | 已完成回滚 |
| `NEEDS_HUMAN` | 自动补偿或验证无法完成，需要人工接管 |

## 14. 管理员安全底线

- 不要把数据库密码、API Key 或员工正式密码写入 Agent 对话；
- 不要把前端按钮显示当作服务端权限证明；
- 不要要求 Agent 创造区域、部门、项目或任意 SQL 范围；
- 不要在分析未激活或身份未解析时放行查询；
- 不要覆盖冲突身份的旧绑定；
- 不要把权限组误解为数据范围；
- 不要为了绕过阻断而扩大数据源账号权限；
- 任何疑似越权、半失败或审计异常，都应进入精确管理页面处理。

当前版本的明确边界是：

```text
“让张三看自己负责的数据”是当前支持的需求。

“让张三看华东区数据”不是当前支持的需求，
除非未来新增区域维度权限模型。
```
